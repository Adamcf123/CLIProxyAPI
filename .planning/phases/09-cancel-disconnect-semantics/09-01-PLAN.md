本 Phase 明确选择方案 A：使用 `status_code=499` 表达 canceled（无 schema 变更，hard cutover）。实现要求：

- 在 `internal/metricsruntime/request_state.go` 建立 canceled 的单一真相：
  - 定义常量（例如 `const statusClientClosedRequest = 499`），并提供小而明确的 API（例如 `MarkClientCanceled()` / `IsClientCanceled()`）。
  - 把“failure > canceled > success”的优先级固化在 RequestState 的写入方法里，避免 handler 结束时的 `state.SetStatusCode(c.Writer.Status())` 把 499 覆盖回 200：
    - 已是 canceled 时，忽略后续 2xx 的 SetStatusCode。
    - 若后续出现明确 failure（非 2xx 或 LastError 非空），允许升级为 failure（例如允许 SetStatusCode 写入 4xx/5xx 覆盖 499，或在 SetLastError 时做一次升级）。
  - 约束：不得通过 `LastError`/`error_info` 表达 canceled（CONTEXT: per-request canceled 时 error 必须为空）。

- 在 `internal/metricsruntime/usage_plugin.go` 把 canceled 稳定落库：
  - 当 RequestState 表示 canceled 时：
    - `MetricRecord.StatusCode` 必须写入 499。
    - `MetricRecord.ErrorInfo` 必须为 nil（即使 request context 的 Err() 是 context.Canceled，也不能写入 error_info）。
  - 同时保证 tokens/metric 聚合不会被 canceled 污染：
    - 至少要保证不会把 canceled 的样本送入 TPSCollector（建议：canceled 时跳过 `CompleteRequest` 与 TPS/TPOT 的计算与回填）。
    - 不引入新参数/新对外能力；仅修正写入侧语义。
  </action>
  <verify>

 rg -n "statusClientClosedRequest|499" internal/metricsruntime/request_state.go internal/metricsruntime/usage_plugin.go
  </verify>
  <done>
- canceled 的持久化信号被定义为 status_code=499，且该状态不会被后续 2xx 覆盖
- canceled 行落库时 error_info 为空（nil）
- canceled 样本不会进入 TPSCollector 的聚合窗口（避免 token/throughput 污染）
  </done>

把 cancel/disconnect 的检测点收敛到两处（RESEARCH 推荐），并统一写入 RequestState（单一真相）：

- Streaming：在 `sdk/api/handlers/stream_forwarder.go` 的 `case <-c.Request.Context().Done():` 分支：
  - 使用 `c.Request.Context().Err()` 区分：
    - `context.DeadlineExceeded` -> failure（不得标 canceled）
    - `context.Canceled` -> canceled（conservative canceled）
  - “上游明确错误优先”为 hard rule：在标记 canceled 前，做一次对 `errs` channel 的非阻塞探测：
    - 若此时已存在 terminal error（errMsg != nil），则按 failure 路径处理（复用现有 `maybeSetStreamingTerminalLastError`），不得写 499。
  - 注意：不得新增对外 endpoint / query 参数；不得把 canceled 写入 error_info。

- 同步更新 `sdk/api/handlers/stream_forwarder_test.go`（使本 Plan 可自验证，不依赖 09-03）：
  - 更新/新增 `TestForwardStream` 中与 cancel/disconnect 相关的断言，锁定语义（锁定不可变）：
    - cancel/disconnect = canceled（status_code=499）
    - timeout（DeadlineExceeded）= failure（不得是 499）
    - upstream error = failure（优先级高于 canceled）
  - per-request canceled 时 error 为空：断言 canceled 路径不设置 LastError / 不通过 error_info 表达。
  - 测试避免依赖 wall-clock：优先用 context cancel/deadline 触发 Done，不使用 sleep。

- Non-streaming（以及 streaming 的补充兜底）：在 `internal/api/middleware/response_writer.go`：
  - 在 `Write` / `WriteString` 捕捉底层 writer 返回的 `err`（仅记录，不改变写出顺序；保持“先写客户端”的零延迟原则）。
  - 在 `Finalize(c)` 中做“最终 outcome”补正：
    - 若 RequestState 已是 failure（非 2xx 或 LastError 非空），不标 canceled。
    - 否则：
      - 若 request context 是 DeadlineExceeded -> failure
      - 若发生过 write error -> canceled
  - 目标是：在服务端未完整写出响应前下游连接断开时，稳定标记 canceled。
