    1) 新增 `.planning/phases/11-runtime-validation/tools/mock_openai_compat_upstream.go`：
       - 启动一个本地 HTTP server（端口可通过 env 或默认值设定；默认 53357）
       - 实现 `POST /chat/completions`：
         - 返回 `200` 并设置 `Content-Type: text/event-stream`
         - 写出至少 1-2 个 `data: {json}\n\n` 事件并 flush
        - 随后**直接断开连接**（不发送 `[DONE]`），用于模拟“headers 已提交后发生 terminal error”
        - payload JSON 可以最小化，但必须包含 `model` 与 `messages` 的基本结构（用于与真实 handler 兼容）。

    2) 新增 `.planning/phases/11-runtime-validation/tools/cancel_stream_client.go`：
       - 用 `net/http` 发起到 CLIProxyAPI 的 streaming 请求（建议 `/v1/chat/completions`，`stream=true`）
       - 读取响应 body 若干字节后主动 cancel context / 关闭 body
       - 退出码与 stdout 输出必须可被脚本解析（例如打印 `CANCELED_AFTER_BYTES=<n>`）
       - 注意：此工具的目的是触发服务端 499 取消语义（Phase 09），不是验证内容正确性。

    3) 新增 `.planning/phases/11-runtime-validation/scripts/run_edge_cases.sh`：
       - 复用 `scripts/lib.sh` 统一创建 run_dir / 启停 server / 采集证据
       - 采用一个**最小临时 config**（写在 run_dir 下，属于 artifacts，gitignored）：
         - host: 127.0.0.1
         - port: 53356（避免与 baseline 冲突）
          - remote-management.secret-key: 来自环境变量 `MANAGEMENT_KEY`（建议默认值为验证专用的 `phase11-dev`；允许写入 artifacts-only temp config，但必须被 .gitignore 命中且不得提交）
         - api-keys: ["sk-dummy"]
         - openai-compatibility: 配置一个 provider 指向 mock upstream（base-url `http://127.0.0.1:53357`），models 至少包含 `mock-stream`
        - edge-case 必须包含四个可运行子命令，并且 `all` 会依次执行全部四项：
          - `terminal-error-after-headers`: 启动 mock upstream + 启动 proxy + 发起 `model=mock-stream` 的 streaming 请求，期待客户端收到部分数据后连接异常结束；随后从 server stderr 的 `metrics_summary` 抽取 `tracking_id` 作为 `request_id`，并在 SQLite 中验证该行存在且满足 failure 语义（`status_code` 为非 2xx 或 `error_info` 非空）。
          - `client-cancel`: 使用 `cancel_stream_client.go` 触发取消；随后验证 SQLite 中该 `request_id` 的 `status_code=499` 且 `error_info` 为空（或 NULL）。
          - `no-usage`: 触发“上游无 usage”的请求路径（允许使用 mock upstream / 最小临时 config），并验证仍产生可查询 SQLite 行（tokens 可能为 NULL，但行必须存在）。
          - `persistence-degraded`: 以**确定性**方式触发持久化 degraded（优先触发 insert_failure）：例如在 proxy 启动后将 run_dir 下 `logs/` 或 `logs/metrics.db` 权限改为只读，或制造 SQLite 写锁/超时，使写入失败可重复发生；随后用 management endpoint 观察 `meta.persistence.degraded` 与最小字段（`last_drop_reason`、`dropped_total` 等），并在 SQLite/日志侧保留证据。
        - 所有 edge-case 必须内置循环 >=3 次（Context 要求），脚本应把每次运行的 `request_id`、预期/实际与证据文件路径写入 evidence 表（TSV/CSV/Markdown 表均可）。
