  <action>
    1) 新建 `internal/api/handlers/management/metrics.go`，实现 `func (h *Handler) GetMetrics(c *gin.Context)`。

    2) 统一端点的查询类型选择（按 locked decision + 本任务约束定稿）：
       - `request_id` 存在时：走单条查询分支，忽略 `mode/from/to/bucket`。
       - 否则要求 `mode` 必须是 `percentiles` 或 `buckets`（本 plan 先实现校验与占位返回；聚合逻辑在后续 plans 实现）。

    3) 输入与默认值（本 plan 需实现完整校验/默认，但聚合结果可暂时返回 501 或结构化占位）：
        - `from`/`to`：RFC3339；若两者都为空，默认最近 1h（`to=now.UTC()`，`from=to-1h`）。
        - 校验：
          - 若只提供其中一个：400（避免隐式推断）。
          - `from >= to`：400。
        - `streaming`：可选；若提供，必须可解析为 bool（accept: `true/false/1/0`）。

        为了让“默认最近 1h”的 meta 回显可以被测试稳定锁定（不依赖真实时间）：
        - 在 `internal/api/handlers/management/handler.go` 的 `Handler` 增加可注入时钟（例如 `nowUTC func() time.Time`）。
        - 生产默认值：`time.Now().UTC()`；测试里设置为固定时间点。

    4) 读路径 DB 连接（必须遵守 research 结论：不要复用 writer 的 *sql.DB）：
       - 在 `internal/api/handlers/management/handler.go` 的 `Handler` 增加只读 DB 的 lazy init 字段（例如 `metricsDBPath`, `metricsReadDB`, `metricsReadOnce`, `metricsReadErr`）。
       - 在 `GetMetrics` 中通过 helper（例如 `h.openMetricsReadDB()`）获得一个专用 `*sql.DB`，指向同一 DB 文件路径（默认 `logs/metrics.db`）。
       - 复用 `metricspersist.InitDB(path)` 以确保 PRAGMA 一致；但不要把该 DB handle 交给 writer。

    5) request_id 查询（必须交付可用能力）：
        - 通过参数化 SQL：`SELECT ... FROM metrics WHERE request_id = ?`。
        - 返回字段至少包含：request_id/provider/model/streaming/status_code/error_info/created_at 以及 TPS/TTFT/TPOT/duration_ms/token 相关列（若为 NULL 则输出 null）。
        - 延迟类指标输出单位：
          - `ttft_ms`, `tpot_ms`：从 DB 的秒（REAL）转换为毫秒整数，并锁定取整策略。

            取整策略（本 phase 锁死，禁止后续 plans 各自实现）：
            - 新建 `internal/api/handlers/management/metrics_units.go`，实现 `func secondsToMillisInt(sec float64) int64`：
              - 计算：`ms := sec * 1000`
              - 取整：使用 `math.Round(ms)`（Go 语义：0.5 远离 0 的四舍五入）
              - 返回：`int64(math.Round(ms))`
            - request_id / percentiles / buckets 三条输出路径必须复用该 helper（禁止 `*1000` 后直接 cast）。
        - 错误：不存在返回 404，格式为 `{"error":"..."}`（跟随管理端既有风格）。

    6) 响应 envelope（本阶段统一 contract，后续 plan 不应再改动）：
       - 顶层：`meta` + `data`（request_id 分支的 data 为单条记录对象）。
       - `meta` 必须回显：`mode`（request_id 分支可填 `request_id`）、`requested_from/to`（若未提供则为 null）、`effective_from/to`（默认后的值）、`filters`（provider/model/streaming）。

    说明：本 plan 可以对 mode=percentiles/buckets 暂时返回 501（Not Implemented）+ `{"error":"..."}`，但必须完成所有校验与 meta 的计算与回显，以便后续 plan 只填充聚合逻辑。
